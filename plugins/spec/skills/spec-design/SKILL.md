# 规格设计对话

通过有重点的协作对话，把想法或已有计划转化为足以指导实施的规格。保持严谨，但不要把固定仪式误当成严谨：问题数量、方案数量和文档篇幅都由任务本身决定。

<HARD-GATE>
在用户确认设计之前，不要编写实现代码、搭建项目或调用实施流程。探索代码库、比较方案、记录设计和编写规格不属于实现。
这道闸门约束的是尚未确认的新设计；已有规格覆盖的改动按下一节直接实现，不受此限。
</HARD-GATE>

## 先判断是否值得开这场对话

触发是概率性的，所以每次进来先花一句话判断：需求是否已经明确、范围是否局部、是否只有一种符合仓库惯例的合理做法。三者成立就不要走下面的流程，直接说明这属于可直接实现的范围并转入实现。加一个展示字段、加一个命令行开关、改文案样式、按既有模式扩展返回值、定位明确的 bug、局部重构、审查或调试都属于这一类。

对已经想清楚的小改动做访谈，比漏问一个问题更伤：用户要的是结果，不是流程。反过来，一旦改动会牵动产品承诺、对外契约、数据模型或跨子系统边界，即使用户说得很笃定，也值得先确认设计立场。

已有规格覆盖的改动同样不用开对话。`docs/specs/` 是已确认设计的记账处，不是审批门：改动落在某份规格的「包含」范围内时直接实现，实现完把那份规格改到与实现一致——新增字段、行为细化、验收变化都要落回原文档，不要新建第二份规格，也不要为此重开访谈。

只有当改动会改写规格的承诺、范围、数据契约或验收标准时才回到设计对话，而且这时只需说明冲突在哪、影响什么、推荐怎么改，一次确认即可，不必重走全套流程。

## 工作方式

### 1. 探索上下文

先读取与任务直接相关的代码、文档、既有规格和项目约束，再提问。寻找相似功能、现有边界、命名与实现惯例，避免建立第二套约定。

探索既有规格时，先读取当前目录 `docs/specs/`；同时兼容读取旧目录 `docs/superpowers/specs/` 中的历史规格，以复用已有决策和项目惯例。旧目录只作为读取来源，新的或修订后的规格统一写入 `docs/specs/`。

区分四类信息：

- **事实**：可以从代码库、配置或文档查明。直接调查，不向用户提问。
- **产品级决策**：会改变用户承诺、产品范围、数据语义、权限、安全/合规等级、不可逆迁移或显著成本。只有这类决定值得打断用户。
- **派生设计**：能从已确认的产品理念、代码库惯例、可逆性和 YAGNI 推导出的架构选择。自行决定并在设计摘要中披露，不逐项询问。
- **实施细节**：函数名、文件拆分、内部状态字段、普通错误处理和测试落点。留给实施计划，不在规格访谈中询问，除非它形成外部契约。

如果需求横跨多个可独立交付的子系统，先指出范围问题，帮助拆成有依赖顺序的规格；不要用漫长访谈掩盖范围失控。

### 2. 先确定设计立场，再推导细节

从目标和成功标准开始，把相关细节聚类为少数上位产品承诺。先询问能同时约束一组下游选择的“设计立场”，而不是沿设计树逐叶追问。

例如异步任务不要依次询问刷新恢复、服务重启、任务 ID、队列和任务列表。先询问用户需要哪一级承诺：页面内异步、可恢复单任务，还是持久化作业系统。选择后自动推导恢复方式、持久化边界和任务模型。

每个上位问题都要：

1. 说明它会约束哪些下游设计；
2. 给出 2–3 个代表不同产品承诺的清晰选项；不适合选择题时才使用开放问题；
3. 提供推荐答案和简短理由；
4. 只询问一个真正的产品级决策，不追加条件式追问。

不设置问题数量上限，但设置**提问价值门槛**。只有同时满足以下条件才询问：

1. 无法从已确认的上位设计立场推导；
2. 无法从代码库惯例或常规默认值确定；
3. 选择会改变用户承诺、高风险边界或不可逆成本；
4. 猜错的返工成本明显高于多一轮确认。

不满足门槛时直接采用推荐设计。复杂事项可能有多个上位问题，但一个问题应消解一组细节，不能把访谈退化成逐字段问卷。

如果用户说“其余按推荐”“你来决定”或同等意思，可采用推荐继续。对不可逆、昂贵、安全敏感或会显著改变产品范围的决定，仍要明确呈现并获得确认。

### 3. 形成推导包，让用户纠偏

每个上位决定确定后，批量推导相关架构和行为，形成一个简短的**推导包**：

- **已确认理念**：用户选择的产品承诺；
- **由此推导**：不再逐项询问的架构、状态和行为；
- **采用默认值**：来自代码库惯例或低风险工程判断的选择；
- **排除项**：为控制范围而明确不做的能力；
- **需要纠正的假设**：只有可能改变产品承诺的少量假设。

把推导包作为整体展示，并说明“除非其中某项不符合预期，将按此继续”。用户无需逐项批准；只有用户纠正某项时才回到相应上位决策。新反馈若与既有决定冲突，指出冲突和影响，请用户选择要修改的上位承诺，不要静默覆盖。

不要把可从理念推导的细节重新包装成问题。不要询问函数、文件、内部状态、常规协议选择或测试组织方式。

### 4. 只比较真实方案

存在两个或更多合理路线时，展示 2–3 个方案及其关键权衡，推荐其中一个并解释原因。只有一个方案符合既有架构、约束和 YAGNI 时，直接提出该方案；不要制造伪选项来满足流程。

比较应聚焦会改变选择的差异，例如复杂度、可逆性、运行成本、迁移风险和用户体验。避免罗列不影响决策的优缺点。

### 5. 收敛并确认设计

当以下条件满足时停止追问：

- 目标、成功标准、范围与非目标明确；
- 产品级承诺和高风险边界已有决定；
- 其余设计可以从这些决定和仓库惯例可靠推导；
- 重要失败行为与验收标准明确；
- 没有会导致两个合理但产品语义不同的实现的关键歧义。

收敛前做一次反证检查：推荐方案在哪些条件下会失败、哪个约束变化会推翻当前选择、是否存在不可逆迁移、验收是否可能全过但仍违背用户承诺。能自行回答的直接纳入设计；只有反证会改变产品级决定时才询问用户。

一次性展示完整设计和最终推导包，篇幅与复杂度匹配。请求一次整体确认，不强制逐节确认。用户明确授权“按推荐直接形成规格”“无需再次确认”时，可把该授权视为整体确认。

### 6. 写入规格

确认后，将新的或修订后的设计写入：

`docs/specs/YYYY-MM-DD-<topic>-design.md`

优先复用该仓库现有规格的结构和语言。没有既有格式时，从下面的伸缩模板开始：

```markdown
# <设计标题>

日期：YYYY-MM-DD

## 背景与目标

## 范围
### 包含
### 不包含

## 已知约束

## 关键决策
| 决策 | 选择 | 理由 |
| --- | --- | --- |

## 设计

## 错误与边界情况

## 验收标准

## 未决事项
```

模板用于提醒，不是必须填满的表单：

- 简单改动可以合并或省略不适用章节；
- 复杂设计可以增加数据模型、协议、安全、迁移、部署等章节；
- 只有图能显著提升理解时才加入 Mermaid；
- `未决事项` 正常应为空；存在外部依赖时，写明责任方和阻塞条件；
- 重要决策直接写入规格，不额外创建 ADR、词汇表或重复文档，除非仓库已有明确惯例或用户要求。

不要自动 commit。只有用户明确要求提交时才提交。


### 7. 分级审查并交付

所有规格先做一次低成本确定性自检并直接修复：

- 没有 TODO、TBD、占位符或未完成章节；
- 各章节没有矛盾，术语前后一致；
- 范围适合一个实施计划，否则已拆分；
- 关键要求不能被两种合理方式理解；
- 验收标准描述外部可观察行为；
- 没有用户未要求的功能或无关重构；
- 文档足以让后续计划阶段确定改哪些边界、验证哪些行为。

然后判断是否需要独立审查。独立审查的成本不在文档长度，而在于审查员没有参与访谈：它要从零重建上下文，会重读仓库、重新推导你已经确认过的事实，把一次校对拖成一次调研。所以调度前先确认它能带回自检拿不到的东西。

自检已经覆盖文档自洽、术语一致、范围可实施和验收可观察。独立审查只在这类风险上有额外价值——设计的正确性依赖多个互相耦合的推导假设，文档自洽并不能证明这些假设成立：

- 不可逆迁移、数据破坏或兼容切换；
- 跨服务或跨重启的状态恢复、幂等与取消语义；
- 认证、权限、租户隔离、配额或计费边界；
- 长期兼容的对外 API 或协议契约；
- 用户明确要求压力测试、review、审查或 grill。

判断要针对这份设计真正的承重点，不是关键词匹配。规格里出现异步、队列或状态机，但恢复语义只有一条明确路径、失败处理没有分支时，自检已经够了，直接交付。

未命中时，完成自检后直接交付，不调度 subagent。

命中时，给审查员一份能直接开工的上下文包，而不是一个仓库加一个问题。你在探索和访谈阶段已经查过这些事实，让它重查一遍是纯粹的重复劳动，也是审查耗时的主要来源：

- 规格文件路径，加上你已确认相关的最多 3 个文件或目录；
- 推导包里的关键假设清单，并标明你希望它优先攻击哪几条；
- 明确禁止在给定路径之外做开放式仓库探索；需要核对仓库事实时只在这些路径内确认；
- 选择可用的最快只读 agent，不要用重型通用 agent；
- 最多 5 条阻塞问题，按影响排序；找到足够的问题就返回，不追求穷尽。

审查范围只保留它独有的能力：对着设计做对抗性阅读。

1. 产品承诺是否都有实现机制闭合；
2. 状态转换、失败、并发、取消、重试和恢复语义是否存在缺口；
3. 下游设计是否与上位决策矛盾，或依赖未披露的假设；
4. 是否可能所有验收都通过却仍违背用户承诺。

不要让它复核代码库惯例、部署约束、范围与 YAGNI 或措辞风格。前两项你有上下文而它没有，它只能靠重读仓库补齐；后两项自检刚做过。重复这些既拖长时间，又会产出上下文不足的误判。

要求审查员使用以下格式：

```markdown
## 规格审查

**状态：** 通过 | 需要修正

### 阻塞问题
- [章节] [具体问题]
  - 影响：[为什么会导致错误实施]
  - 最小修正：[最小修正方向]

### 非阻塞提醒
- [真实风险；没有则写“无”]
```

校准审查边界：只标记会改变实施正确性的问题。不要重写整份规格，不因个人架构偏好否决可行方案，不要求无关章节，不点评措辞风格，也不要把派生实现细节重新升级成用户问题。

独立审查最多一轮。若状态为“通过”，直接交付。若存在阻塞问题，修正规格并重新执行确定性自检；除非修正改变产品承诺，否则不重新询问用户，也不再次调度审查。非阻塞提醒不触发修改循环。

因审查而改动规格时，交付里要能看出改了什么。用户没有看到审查报告，规格已经变成新版本，「发现若干问题并已修正」对他等于什么都没说——他无法判断改动是否符合他确认过的设计，也无法在你改错时纠正你。所以对每处改动给一行说明：

`[章节] 原来怎么写 → 现在怎么写（因为：审查指出的影响）`

一行一处，按章节顺序排列，用具体内容而不是问题类别。对你判断不成立、因而没有采纳的阻塞问题，同样一行说明为什么不改（与哪条已确认决策、非目标或代码库事实冲突）——否则用户只会看到一个静默变短的问题清单。这份说明是给决策看的，不是变更日志：不要罗列措辞调整，也不要复述整段新内容。

交付时说明规格路径、是否经过独立审查、上述改动说明、关键决定和仍存在的阻塞。等待用户要求修改或进入后续计划；不要自行开始实现。

## 核心原则

- **事实先查，决策才问**：把用户时间留给真正需要判断的事情。
- **一次一个问题**：保持决策依赖清晰。
- **每问必有推荐**：不仅暴露问题，也提供专业判断。
- **深度随复杂度变化**：不限制问题数，也不制造问题。
- **理念优先**：先确定能约束一组细节的产品承诺，再批量推导。
- **用户定承诺，Agent 定实现**：只把产品语义和高风险边界交给用户。
- **推导包纠偏**：集中披露假设和默认值，代替逐项审批。
- **提问看价值，不看数量**：不限制复杂度，但每问都必须改变产品设计。
- **方案必须真实**：不为满足数量而虚构替代方案。
- **一次整体确认**：避免逐节审批造成的流程疲劳。
- **规格服务实施**：记录足够的约束和可验证结果，而不是追求文档篇幅。
- **审查按价值付费**：自检覆盖文档质量；只有承重推导无法自证时才调度一次独立只读审查，并给定上下文包与产出上限，不让它重建你已有的上下文。
- **改动可追溯**：因审查改了规格就逐处说明改前改后与理由；用户看不到审查报告，只能靠这份说明纠正你。
- **严格 YAGNI**：只设计当前目标需要的能力。
