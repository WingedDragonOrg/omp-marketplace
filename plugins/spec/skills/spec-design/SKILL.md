# 规格设计对话

## 先选路径

遵守用户要求的阶段：只要求设计就不实施；要求实施不等于授权改变已确认的产品承诺。

- **直接实施并核对规格**：需求明确、按既有决定即可实施时，不开设计对话。即使是小改动，也先定位它是否落在某份规格的覆盖范围内；实现后、交付前对照实际结果，把新增字段、行为细化和验收描述的变化同步到生效规格。内容已一致则不改；没有相关规格时不为小改动新建。
- **确认一次变更**：若会改写已确认的承诺、范围、对外契约或验收标准，指出冲突、影响和推荐处理；只确认变化的决定，不重开整套访谈。补足验收描述与改变验收标准不是一回事。
- **设计**：产品级决定尚未收敛，或用户明确要求先设计、梳理或审查计划，就按下文工作。未确认的设计不要写实现代码、搭项目或启动实施；探索、对比和撰写规格不算实施。

先查直接相关的实现、约束和现有规格。优先读 `docs/specs/`，再从 `docs/superpowers/specs/` 读取历史决策。已存在当前规格时以它为准；历史原件只读。

## 用最少的提问定下产品承诺

1. **查事实，推导细节。** 库内可查的事自行核实；能够从已确认目标、仓库惯例或低风险默认值推导的架构和行为自行决定并披露。函数名、文件拆分、内部状态和测试落点留给实施，除非它们是对外契约。
2. **只问无法推导、且猜错代价高的决定。** 用户通常只需要决定产品语义、权限、安全、不可逆迁移或显著成本。一次问一个能约束多个下游选择的问题，给推荐和理由；有真实取舍时给 2–3 个选项，不凑数。例：先问是否承诺重启后继续处理已接收的任务，而不是逐项问队列、任务 ID 和存储。
3. **控制范围。** 多个可独立交付的子系统按依赖拆分，先确认上游边界。不限制有必要的提问数量；用户授权按推荐继续时采用推荐，但仍明确确认尚未决的不可逆、昂贵、安全敏感或显著改变产品范围的选择。
4. **集中披露，不逐项审批。** 在设计摘要里归拢已确认承诺、推导出的行为和架构、采用的默认值、非目标，以及会改变产品承诺的假设。反馈冲突时指出它改动了哪项承诺和影响，不静默覆盖。

目标、范围、失败行为和可观察验收清楚，并且不会导出两种产品语义不同的实现时，停止追问。做一次反证：哪些条件会让方案失败，是否存在不可逆切换，验收全过是否仍可能违背承诺。然后给完整设计做一次整体确认；用户已明确确认或授权直接形成规格，且没有上述高风险未决项时，不追加确认。

## 写入或同步生效规格

- **新规格**：确认后写 `docs/specs/YYYY-MM-DD-<topic>-design.md`。
- **已有当前规格**：在 `docs/specs/` 内就地更新，不另起一份；无需同步时保持原样。
- **仅有历史规格**：原件留在 `docs/superpowers/specs/`，不修改、不移动、不删除。需要修订时，在 `docs/specs/` 以同名写入唯一的生效版本，保留原需求记录、标明历史来源；之后引用当前版本。无需修订时不复制。

优先复用仓库已有版式和语言。正文写到能实施和验收即可：目标、范围和非目标、约束、关键决策、设计、重要失败行为、可观察验收；只有外部依赖确实阻塞时才记未决事项与责任方。仅在能让设计更好懂时附图；不额外建 ADR、词汇表或第二份规格，除非仓库约定或用户要求。

### 用户原始需求

每份规格都保留独立的「用户原始需求」章节。按对话顺序编号引用与本规格有关的需求、补充和确认，尽可能逐字保留；标明补充和替代关系，敏感信息脱敏并标出位置。修订时保留历史记录并追加本次需求。原文与归纳、派生设计分开，验收用编号或明确引用关联到当前有效的要求或确认决定。

## 自检、审查与交付

**先自检**：清理占位和未完成章节；核对需求原文及替代关系、当前决定、术语和范围；确保每项关键承诺都有可观察的验收，文档足够实施、没有无关功能或重构。

**再看是否需独立审查**：用户明确要求时，或设计正确性依赖自检无法证实的耦合假设时才审查。典型承重点：不可逆迁移或兼容切换、跨服务/跨重启恢复及幂等/取消、权限/租户/计费、需要长期兼容的外部契约。光有异步、队列或状态机等关键词不算。其余通过自检后直接交付。

独立审查只调度一轮：选最快可用的只读审查员，给规格、最多 3 个已确认相关的文件或目录，以及要反证的关键假设。禁止开放式探索；不重复审查既有仓库惯例、部署约束、范围/YAGNI 或措辞。只找会导致错误实施的缺口：承诺是否有机制闭合，状态转换、失败、并发、重试和恢复是否有漏洞，以及验收能否全过却违背承诺。返回通过/需修正、最多 5 条按影响排序的阻塞（章节、影响、最小修法），非阻塞提醒单列。

修正成立的阻塞后重做自检，不追加审查轮次；只有修正改变已确认承诺时才回到用户确认。非阻塞提醒不触发返工。

交付规格路径、关键决定、审查状态和剩余阻塞。若因审查调整，按章节逐处写「原来 → 现在（理由）」；未采纳的阻塞也解释依据。用户只要求设计时在此收手；只有用户授权才继续实施或提交。
