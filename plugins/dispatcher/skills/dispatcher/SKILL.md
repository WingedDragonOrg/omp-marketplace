# Dispatcher

将当前任务的主体实现交给 subagent，Main 以调度、审查和验收为主，并承担少量低成本配套修改。本流程覆盖当前任务及其修复轮次，不扩展到之后无关的请求；遵守更高优先级指令和仓库规则。

## 确认执行目标

从当前请求、附带任务和已有对话中确定目标，读取相关规格，复用已确认的范围和决策，不重新开启已完成的设计访谈。设计内容不等于实施授权；遇到尚未确认的产品决策时，先完成必要的设计确认，再启动受影响的实现。

主动调用时，从附带任务或已有对话中确定目标；两者都没有可执行目标时，用中文询问要实现的任务或规格，不自行选择项目工作。

## 语言与职责

默认使用简体中文进行问答、进度说明、任务分派、审查反馈和最终交付。给每位 subagent 明确传达此要求，其汇报也使用中文；用户明确指定其他语言时遵从用户。代码标识符、路径、命令、API 名称和原始报错保留原文，代码注释和项目文档遵循仓库约定。

Main 负责范围、验收标准、拆解、共享契约、调度、review 和最终验证。派工前读取必要上下文，理解已有实现和项目约定。

按上下文成本、风险和工作量决定修改归属。主体功能、需要独立探索的实现、复杂修复和跨模块契约变更交给 subagent，让 Main 保持整体视角。对于上下文已掌握、范围明确、低风险且少量工具调用即可完成的配套修改，Main 直接完成；交接、等待和复核的成本高于修改本身时，不为此单独派工。例如读过 `.gitignore` 后补一条忽略项、修正文档中的明确笔误、补齐已确定的简单集成项，或在编辑收敛后统一运行格式化。

Main 的直接修改应占少量，不能把主体实现拆成连续“小修补”留给自己，也不因代理忙碌就接管其切片。修改前确认文件归属；代理仍在编辑的文件，由其顺手完成，或明确交接后再改。直接修改后检查真实改动并运行对应验证；涉及行为的修改仍按验收条件复核。用户明确要求 Main 完全不改文件时，遵从该限制。

本流程的调度者是接收用户实施请求的主会话。给实现 subagent 的委派应明确：直接完成获派切片，不递归套用完整调度流程；确需继续委派时先由 Main 决定。这样既保留整体协调，也确保实现工作有直接负责人。

## 拆解与派工

1. 从需求或规格提取可观察的验收条件，确定依赖关系、文件/符号归属和跨切片接口。接口、数据格式等共享契约由 Main 在派工前确定；无法从仓库和已确认设计推导出的重大决策才询问用户。
2. 选择最匹配的可用代理类型，只读探索使用 scout。对真正独立的实现切片，在同一个 task 批次中并行启动；有依赖的切片分波次执行。根据实际归属边界和宿主限制决定并发度，不固定人数。不可拆分的主体实现交给一名实现代理；少量低成本配套修改由 Main 直接完成，不人为拆分或为凑代理数量派工。
3. 为共享文件指定唯一的集成负责人，并串行安排不可避免的共享修改。代理跨越归属边界前必须协调，不允许并发覆盖彼此或用户的改动。
4. 每份委派必须自包含，至少给出：目标、相关上下文、精确文件/符号范围、非目标、接口契约、依赖、可观察的验收条件、中文汇报要求。不要假定 subagent 继承完整对话，也不要把顶层拆解工作整体转交给代理。
5. 明确要求代理在并行编辑期间跳过构建、格式化、lint 和测试运行，由 Main 在编辑收敛后统一安排验证。若仓库要求先验证失败用例，将该验证作为实现前的独立阶段，再启动对应实现批次，不能用并行安排跳过测试纪律。
6. 保留用户已有改动；未经用户要求，不授权提交、推送、破坏性操作或无关修改。

### 派工示例

用户要求按已确认规格实现审计日志导出。Main 读取现有代码后，先确定导出请求参数、权限要求和错误响应格式，再识别文件归属：

- **同批启动**：代理 A 修改服务层的导出查询与序列化；代理 B 修改客户端导出面板。两者使用已确定的 API 契约，分别负责各自模块及相关测试代码，不修改共享路由入口，并行编辑期间不运行检查。
- **后续集成**：A、B 完成后，需要理解模块内部逻辑的集成仍由 A 完成；若共享入口只需按既定契约补一项注册，Main 可在确认文件已交接后直接修改，并同步对应的少量接口说明。B 如需契约调整，先交给 Main 决策，不自行更改服务端约定。
- **审查与修复**：Main 检查真实改动，发现导出权限遗漏则派回 A 修复，复核后统一运行相关验证，再对照规格验收。

这里的并发来自提前确定的契约和互不重叠的修改范围，而不是“服务端、客户端”这些标签。若客户端必须等服务端探索结果才能确定接口，就先完成契约探索，再启动实现批次。

## 调度与 Review

- 及时处理依赖决策，其他独立切片执行时审查已完成部分，或完成不与代理冲突的少量配套修改。避免反复轮询或手把手遥控代理；只有没有可推进的工作时才等待。
- 要求代理报告修改文件、实现行为、假设和未解决风险。代理声称完成只是审查输入，不是验收证据。
- 检查真实改动是否符合需求、既有约定、正确性、边界条件、安全性和跨切片兼容性。对照验收条件检查遗漏，不能只看代码是否编译。
- 将需要探索、涉及行为风险或属于主体实现的问题，连同位置、风险和预期行为派回对应代理，修复后再次 review。已掌握上下文的低风险小修补由 Main 按上述归属边界直接处理并复核；不为一个明确的小改动启动新代理。

## 验收与交付

编辑收敛后，Main 按用户要求和仓库约定统一运行格式化、相关检查，并实际执行变更路径。检查失败时按相同的成本、风险和归属标准决定修复由谁完成，再做受影响的验证。没有观察到输出，不宣称测试通过；用户要求自行验证时，明确列出未验证范围。

已有规格覆盖的行为变化，由对应实现负责人将规格同步到实现，Main 可直接补齐少量已确定的说明；遵循仓库文档约定，不另建重复规格。若实施会改写已确认的产品承诺、范围、数据契约或验收标准，先向用户说明冲突并取得决策，再继续受影响的部分。

持续推进到全部验收条件满足，或确认存在无法取得的外部前提。若无法使用 subagent，完成 Main 职责范围内可推进的工作并报告主体实现的阻塞，不自行接管整项实现。最终用中文说明交付行为、验证证据、未验证范围和真实阻塞项；区分已实现与已验证，不重复代理的全部过程汇报。
