# Octo Loop 任务评论原生工具设计

日期：2026-11-11

## 用户原始需求

1. “能否这样，现在是 octo://<docId> 能否改成, octo://docs/<docId>, 接下来还要做 octo://drive/xxxx   octo://loop/tasks/<xxxxxx> 具体路径定义你可以调研下给我设计参考。”
2. “还要支持 octo loop task的 comment 读取、编辑、写入、回复、附件等。”本条补充 Loop 评论和附件能力。
3. 对评论编辑的并发保证，选择“尽力检查：提交前重新读取并比较，但承认检查与提交之间仍可能覆盖他人的修改。”
4. 对附件交互，选择“混合方式：评论使用原生工具；二进制附件上传、下载继续调用 octo-cli。”
5. 对 Docs 路径切换、包含 workspace 的 Loop 路径、评论能力、尽力并发检查、附件混合方式及 Drive 后续设计的整体方案，选择“确认，修订规格”。

## 范围与依赖

在 `plugins/octo` 的同一个原生工具扩展中增加 Loop 任务和评论能力，远端调用通过 `octo-cli`。先完成 `2026-11-10-octo-native-tools-design.md` 中的 Docs 路径切换，再接入本规格；同一 `octo://` 路由按 authority 分派，不能让 Docs 解析器拦截 Loop 路径。Drive 为独立的后续设计，不在本规格实施。

支持任务及评论读取、已有评论正文整体写入或 hashline 编辑、发表新评论和回复，以及读取评论返回的附件信息。附件二进制上传和下载使用 `octo-cli loop attachment upload/download`，不把本地路径或二进制数据伪装为原生 `write` 的文本内容。评论删除、reaction、resolve/reopen、任务状态变更及派发不在本规格范围。

## 路径与工具行为

`<ws>`、`<task>`、`<comment>` 为完整 UUID，workspace 是 CLI 必需的独立作用域；不依赖当前目录或隐式 workspace 推断。路径段按 URI 编码规则处理。以下 `...` 仅是表格中的前缀缩写，实际请求使用完整路径。

| 路径 | 工具 | 行为 |
| --- | --- | --- |
| `octo://loop/workspaces` | `read` | 列出当前身份可访问的工作区 |
| `octo://loop/workspaces/<ws>/tasks` | `read` | 列出工作区任务 |
| `octo://loop/workspaces/<ws>/tasks/<task>` | `read` | 获取任务详情 |
| `octo://loop/workspaces/<ws>/tasks/<task>/comments` | `read` | 列出任务评论及服务端返回的回复关系、附件信息 |
| `octo://loop/workspaces/<ws>/tasks/<task>/comments/<comment>` | `read`、`write`、`edit` | `read` 返回评论正文；`write` 整体替换正文；`edit` 使用 read 返回的 hashline 修改正文 |
| `octo://loop/workspaces/<ws>/tasks/<task>/comments/new` | `write` | 发表新评论 |
| `octo://loop/workspaces/<ws>/tasks/<task>/comments/<comment>/replies/new` | `write` | 回复指定评论 |

列表和任务详情以 JSON 呈现，并保留 CLI 返回的资源字段。评论正文以原始文本呈现，支持原生行范围及 hashline；元数据、回复关系和附件信息从评论列表获取，不把显示性字段混入可写正文。列表逐页读取 CLI 实际响应的 `pagination`，直至取得全部页；无法完成时返回错误，不把部分结果伪装成完整列表。按评论 ID 定位时同样遍历评论页，并确认该评论属于路径中的任务；找不到、不可访问或任一分页失败均不提交写入。分页期间并发变化可能影响列表一致性，不声称列表是服务端原子快照。

创建和回复的 `write` 内容为 JSON 对象：必填非空字符串 `content`；可选 `attachment_ids` 和 `suppress_expert_ids` 为 UUID 字符串数组。回复路径中的 `<comment>` 对应 CLI 的 `parent_comment_id`；请求体不再接受第二个父评论选择器。`attachment_ids` 指向已经通过 CLI 上传的附件。写入已有评论的内容则是替换后的正文文本，不接受用于变更状态或附件的 JSON 指令。CLI 的 `comment.update` 当前 schema 未列出具体字段；实施时必须用真实 CLI 和服务端确认正文更新字段与响应，再以该契约实现，不得把猜测的请求当作已验证行为。

## 并发、审批与失败

- 已有评论的 `edit` 必须基于本会话最近一次完整或按行读取所得的 hashline 快照，未见行和本地过期快照拒绝；`write` 为显式整体替换。请求发起时固定本次操作的读取快照、资源和身份，审批等待期间的其他读取不能替换该基准。两者提交前都重新读取目标评论，将当时正文与该固定快照的服务端正文比较；不同则停止并要求重新读取。未先读取的已有评论写入拒绝。
- 此检查是**尽力而为**：当前 CLI 未声明评论条件更新接口，重读与 PATCH 之间的竞争仍可能覆盖其他修改。不得宣称原子比较写入、服务端版本保护或绝不会覆盖并发修改。读取时的评论 ID、任务 ID、workspace 和当前身份共同约束快照；不能跨会话、工作区或身份复用。
- 所有远端写入仍通过 OMP 写审批和 plan mode。创建或回复评论可触发通知或 expert / expert-team 执行；不得静默删除或新增 mention，不得自动改变 `suppress_expert_ids`。按 CLI 的 comment preview 契约预览触发信息；预览、审批和提交绑定同一身份、workspace、任务、父评论、正文、附件及 `suppress_expert_ids`。审批展示这些实际参数和预览的触发结果，包括明确的空抑制列表。预览失败，或响应缺少权威契约要求的解析结果与触发对象信息而无法确认副作用时，停止提交；预览响应字段须按实施时验证的服务端契约判定，不能把缺失字段当成空结果。
- 创建、回复、更新一旦发出后发生超时、取消或连接中断，服务端结果可能未知：明确提示重新读取核实，不自动重试创建或回复，不把未知结果当作成功或确定失败。相同正文可能由其他请求产生，不能仅凭其存在认定未知请求已成功。已确认成功但后续读取失败时，如实报告已确认提交及验证失败。
- `octo-cli` 的身份、workspace、权限和错误原样传递；沿用 Docs 插件已确认的 profile 与环境变量优先级。不得因为权限失败而切换身份或工作区。
- 写入路径仅接受对应操作；列表和详情路径不能通过 `write` 或 `edit` 修改。涉及多个目标的 Loop 补丁若不支持，必须在任何目标写入前明确拒绝；若支持，中途失败或取消时逐目标区分已确认成功、确定失败、结果未知和未尝试，不声称跨资源原子提交。

## 验收标准

1. 使用真实 OMP 与 `octo-cli`，验证工作区、任务和跨页评论读取；目标评论的正文、回复关系及附件信息可按上述路径获得。未知任务或不属于目标任务的评论不能被误读或误写。（需求 1、2）
2. 已有评论的 `read`、`write`、hashline `edit` 均能更新指定正文并保留其他评论；本地未见行、失效快照及重读时检测到的正文变化被拒绝。请求基于 A 等待审批期间远端变为 B 且同会话重新读取 B 时，该请求仍须按固定的 A 检查并拒绝。测试明确保留检查与提交之间仍有竞争的限制。（需求 2、3）
3. 新评论、指定父评论的回复和关联已有附件分别通过 JSON `write` 创建；审批显示目标、正文、附件、抑制列表和完整 mention 预览，参数变化须重新预览和审批；预览缺少必要触发信息时不提交。失败或结果未知时不会被伪报成功或自动重复发表。（需求 2、4、5）
4. 文档化并以真实 `octo-cli` 验证附件上传和下载；评论列表中的附件标识与 CLI 使用的标识一致。插件不把附件二进制上传或下载冒充原生文本写入。（需求 2、4）
5. 本地文件、其他 URI 和 Docs 原生工具行为、审批及 profile 选择不受影响；多目标补丁要么在任何写入前拒绝，要么在部分失败时逐目标正确报告已确认成功、确定失败、未知和未尝试。通过针对性自动化测试及真实 CLI/OMP 契约验证；远端写入仅使用明确获准的测试任务。（需求 1、5）

## 外部依赖

CLI 的 `comment.update` 请求 schema 为开放对象，正文更新字段、权限、mention 预览和服务端响应需要在实施前通过真实后端或其权威契约确认。若缺少该信息或获准的测试任务，不得声称评论更新的真实服务端验收通过。
